        "questions": {

            "tone": {"type": "score", "instructions": "How angry is `review`?", "criteria": ["Calm", "Annoyed", "Furious"]},
        },
    }).encode(),
    headers={"Authorization": f"Bearer {os.environ['SUBQ_API_KEY']}", "Content-Type": "application/json"},
)
for attempt in range(4):
    try:
        print(json.load(opener.open(req, timeout=60))["answers"])
        break
    except urllib.error.HTTPError as e:
        if (e.code != 429 and e.code < 500) or attempt == 3:
            raise SystemExit(f"{e.code}: {e.read().decode()}")  # body: {"detail": {"error_type", "message"}}
        time.sleep(2 ** attempt + random.random())

## 2. Search: one request per query, with all 40 items as options

Use a single `choice` where each item ID is an option and its description is the title plus the catalogue description. Don't send 40 separate yes/no questions: that breaks the 16-questions-per-request limit, and the answers wouldn't be comparable with each other. If you later want a ranking, sort the returned `probabilities`, which you get for free.

I added a `no_match` option because a choice always picks something. Without it, a query for something you don't sell would still get a confident-looking answer. Leave it out if the business rule is "always return an item".

```json

  "state": { "search_query": "wireless earbuds for running" },
  "questions": {
    "best_item": {
      "type": "choice",
      "instructions": "Which catalogue item best matches what the user is looking for in search_query? Pick no_match if no item would reasonably satisfy the query.",
      "criteria": {
        "SKU_0001": "AeroFit Sport Earbuds: wireless, sweat-resistant earbuds with ear hooks, 8h battery",
        "SKU_0002": "StudioMax Over-Ear Headphones: wired closed-back headphones for monitoring",
        "SKU_0003": "BrewMaster 12-Cup Coffee Maker: programmable drip coffee maker with thermal carafe",
        "…": "… 37 more items, each 'Title: short description' …",
        "no_match": "None of the catalogue items fits the query"
      }
    }
  }

```

The catalogue is the same every time, so build this `criteria` object once in code and only swap in the `search_query`. Use short, stable IDs as option names and keep the descriptions to the details that tell items apart. Long marketing copy adds tokens without improving matches. At roughly 50 tokens per item, a request is about 2–3K input tokens, which at $0.05 per 1M tokens is about $0.0001 per query. Check that against `usage.input_tokens` once you're live.

## 3. Deciding when to trust an answer

The API makes no calibration claims, so set the cutoffs from your own labelled data, separately for each question.

1. **Label a sample.** Take a few hundred reviews and queries you already know the answers to, run them through, and store the raw probabilities.
2. **Choose cutoffs per question** by plotting accuracy against how many cases get handled automatically:
   - **Spam (`noul`):** use two cutoffs. Above a high one (say 0.9), filter it automatically. Below a low one (say 0.1), treat it as genuine. Anything in between goes to a person. A value near 0.5 means the model is unsure; it doesn't mean "somewhat spammy".
   - **Category (`choice`):** accept when `confidence` is above your cutoff. Also check the gap between the top two `probabilities`, since a narrow gap like kitchen 0.45 vs office 0.40 is a coin flip. Send low-confidence answers and `other` to review.
   - **Anger (`score`):** use the weighted score directly, e.g. escalate at ≥ 4 (with your 1–5 mapping), plus `confidence`. A low confidence spread across "Frustrated" and "Furious" still points toward escalation. Decide based on whichever mistake costs you more: missing an angry customer or escalating a calm one.
   - **Search (`choice`):** if `confidence` and the top-two gap clear your cutoffs, return the top item. Otherwise show the top 3 items by probability, or fall back to your keyword search. A `no_match` winner means show no result.
3. **Keep the raw probabilities in your data** so you can retune cutoffs without rerunning anything.
4. **Re-check now and then.** Snap is in public preview, so its behaviour can change, and answers can differ slightly between calls. Rerun the labelled set occasionally and after any model change.

The client should retry 429 and 5xx errors with backoff, treat 400 and 422 as bugs in the request, and read the key from the `SUBQ_API_KEY` environment variable. Reviews may contain personal data, so check SubQ's [data-retention page](https://docs.subq.ai/markdown/using-the-api/data-retention.md) before sending production traffic.

## How many requests

- **Reviews: 1 request per review.** All three questions are about the same review text, so send them together (the limit is 16 questions per request). The review text is sent once and the answers come back by question name.
- **Search queries: 1 request per query.** The text being judged is the query. The 40 items go in as options with their titles and descriptions. A choice question allows up to 255 options, so 41 fits easily.
- So N reviews plus M queries take N + M requests. A review and a query have different text, so they can't share a request.

The docs don't say whether questions in one request influence each other, so treat each answer as independent. For example, the anger question shouldn't assume the review is genuine. Combine the answers in your code: if the spam probability is high, drop the category and anger.

**Cost:** you pay only for input tokens, at $0.05 per 1M. The catalogue question is roughly 40 × ~80 tokens, about 3–4K tokens per query, which works out to about $0.0002 per query. Measure `usage.input_tokens` on real requests to confirm.

## 2. Search: 1 request per query, 1 `choice` with 40 options

To pick the best of N candidates, use one `choice` question with the candidates as options. Don't send 40 separate yes/no questions. Use your item IDs as option keys and put each item's title and description in the option's description:

```json
{
  "model": "subq-snap-preview",
  "state": { "search_query": "wireless earbuds for running" },
  "questions": {
    "best_item": {
      "type": "choice",
      "instructions": "Which catalogue item best matches what the shopper is looking for in search_query? Pick no_match if none of the items would satisfy the query.",
      "criteria": {
        "sku_1001": "Trailrunner Sport Earbuds: sweat-resistant Bluetooth earbuds with ear hooks, 8h battery",

        "sku_1003": "Camp Kettle 1L: lightweight aluminium kettle for camping stoves",

        "no_match": null
      }
    }

```

- **The `no_match` option** is optional. Without it, the model has to pick an item even for queries that match nothing. With it, you can tell a weak match apart from no match at all. Drop it if every query is guaranteed to match something.
- **Batching queries into one request:** you could fit up to 16 queries into one request, but each question would have to repeat all 40 descriptions, which saves nothing. Keep one query per request.
- **Top-k results:** if you later want the top 3 instead of just the best, sort the items by their `probabilities` values. One request gives you the ranking.
- **Cost estimate:** 40 short descriptions come to roughly 2–3K input tokens. At $0.05 per 1M input tokens that's about $0.0001–0.00015 per query, and output tokens are free. Check this against `usage.input_tokens` once you're making real calls.

## 3. When to trust an answer

What you get back is guaranteed to have the right shape, not to be right. Pick your cutoffs from labelled data:

1. **Label a sample.** Use a few hundred reviews and queries where you know the correct spam flag, category, anger level and best item. Run them through Snap and store the raw probabilities, not just the top answer.
2. **Set cutoffs separately for each question:**
   - **Spam (`noul`):** use two cutoffs. Above the high one, flag automatically; below the low one, pass automatically; send everything in between to review. Choose the high cutoff from the false-positive rate you can accept, because dropping real reviews usually costs more than missing some spam.

## Reviews

| Need | Question type | Why |
|---|---|---|
| Spam? | Binary (yes/no) | Two outcomes, and you'll want a separate threshold because false positives and false negatives cost different amounts |
| Category | Single-choice, 6 options | The categories don't overlap and "other" covers anything left over |
| Anger | Rating scale 1–5 with labelled anchors | It's ordinal, and labelled anchors make the scores more consistent |

**Requests:** Run them as a gate. Ask the spam question first, then ask category and anger only for reviews that aren't spam.
- If Snap allows one question per request: 1 request for spam, plus 2 more for non-spam reviews. That's 3 at most and about 1 + 2×(non-spam rate) on average.
- If Snap lets you batch several questions in one request: 1 request with all three questions, then ignore category and anger for spam.

## Search → best of 40 items

Use a **single-choice "select best match"** question. How you send it depends on Snap's option limit:
- **Recommended (1 request per query):** First narrow the 40 items to about 8–10 with cheap retrieval (embeddings or BM25 over title + description). Then ask one question with those candidates plus a "none of these" option. Long option lists hurt accuracy and add position bias, and with 40 items this is cheap to do locally.
- **If Snap accepts 40 options:** 1 request, but test it for position bias (see below).
- **If it doesn't and you won't pre-filter:** run a tournament: 4 groups of 10, then a final among the 4 winners. That's 5 requests per query.

## Deciding when to trust an answer

1. **Build a labelled set first.** Hand-label about 200–500 reviews and about 100–200 queries. You can't set thresholds without one.
2. **Use the confidence signal:**
   - If Snap returns per-option probabilities or confidence, use the top score for spam and anger.
   - For category and best-match, use the margin between the top two options (top-1 minus top-2).
   - If it returns nothing, ask 3 times (with options reshuffled for the choice questions) and use the level of agreement.
3. **Set a separate threshold for each question.** Use the labelled set to pick the threshold that reaches your target precision:
   - **Spam:** use a stricter threshold for "spam" if deleting real reviews is the worse mistake.
   - **Anger:** trust it if the answers spread by ≤1 point. Otherwise use the expected value or send it for review.
   - **Category:** route anything with a margin below the threshold, or with "other" winning by only a little, to a human.
   - **Best-match:** shuffle the candidate order and ask again. If the winner changes, don't trust it. Treat "none of these" as a valid answer, not a failure.
4. **Send low-confidence items to human review,** feed the corrections back into the labelled set, and re-check your thresholds periodically.

def decide(state, questions: dict, key: str, *, attempts: int = 5, timeout_s: float = 60.0,
           base_delay_s: float = 1.0, max_delay_s: float = 30.0) -> dict:
    data = json.dumps({"model": MODEL, "state": state, "questions": questions}).encode()
    headers = {"Authorization": f"Bearer {key}", "Content-Type": "application/json"}
    for attempt in range(attempts):
        last = attempt == attempts - 1
        try:
            req = urllib.request.Request(URL, data=data, headers=headers, method="POST")
            with _OPENER.open(req, timeout=timeout_s) as resp:
                return json.load(resp)

                raise SnapError(e.code, err_type, msg) from e  # 400/422/3xx: retrying won't help

        "urgent": p_urgent > 0.5,
        "urgent_probability": round(p_urgent, 3),
